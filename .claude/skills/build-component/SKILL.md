# Build-component
Generate and edit custom Embeddable components as a React component (`index.tsx`) plus an `*.emb.ts` descriptor that declares the component's `meta` (the inputs the no-code builder exposes), its data loading, the mapping from inputs to React props, the events it emits, and the variables it auto-creates. On `embeddable:push` each component becomes a new component version available in the no-code builder.

A component is a **reusable building block, generic over its data.** `meta` declares *typed input slots* (`dataset`/`dimension`/`measure`) and the **dashboard author binds concrete cube members in the builder** — so you design the slots and the data *shape*; you never pick (or ask the user) *which* specific dimension/measure to show. A slot accepts **any** member of the right type (narrow with `config.supportedTypes` only where the viz needs one, e.g. a `time` axis). **The component needs no data model to build or preview** — it previews on the library's generic `previewData.*` mocks, so it works even in a repo with no `*.cube.yml` at all. A concrete member only enters at the dashboard author's config time (or in an optional `defaultValue` when the repo happens to have cubes).
## Prime directive: build ON Remarkable Pro, don't reinvent it
Almost every customer runs on `@embeddable.com/remarkable-pro`, and that library is where i18n, locale/timezone-aware formatting, consistent chart colors, gap-filled time series, the standard card chrome, and the **hover/touch interaction a chart is expected to have** come from **for free**. A custom component that hand-rolls these silently loses all of them and won't match the rest of the dashboard.
**So: before writing any custom logic, reach for the Pro built-ins.** Every generated chart/control must wire in the relevant ones from [references/pro-builtins.md](references/pro-builtins.md):
- `useTheme()` → `i18nSetup(theme)` → `resolveI18nProps(props)` at the top of render
- `getThemeFormatter(theme).data(dimensionOrMeasure, value)` for **all** value formatting
- `useFillGaps({ results, dimension })` for any time-series chart
- colour: **value colours** (data-driven — a dimension value / measure) via `getChartColors()` + `getDimensionMeasureColor(...)` (theme palette + `backgroundColorMap`, **never** CSS tokens); **chrome** (text/borders/accents) via component-token → base-token CSS fallbacks ([pro-builtins.md](references/pro-builtins.md) · [theming.md](references/theming.md))
- `ChartCard` (charts) / `EditorCard` (controls) as the outer wrapper
- the shared `inputs` / `subInputs` constants to compose `meta`, instead of writing input objects by hand
The single biggest failure mode for this skill is generating a "plain React" component that ignores this layer. Don't.

**Reuse is the foundation, not a cap on behaviour.** Inherit the plumbing *and* the expected behaviour: a data-viz the user calls a "chart" must reveal a mark's value on hover/touch the way every Pro chart does, so build on a real charting foundation rather than reimplementing that layer worse — or dropping it (a hand-rolled illustration that can't reveal its own values isn't "building ON Pro", however faithful its tokens). But reuse does **not** limit what the component *does*: its features, interactions, and payloads follow the **user's actual requirement**, and when that requirement is genuinely new, build it — don't force it into an ill-fitting existing pattern. The two failure modes are equal and opposite: reinventing the plumbing, and refusing to build what was asked. (Depth: [references/events-and-state.md](references/events-and-state.md) → "Emit what the requirement needs".)
## File location
New components live in `src/embeddable.com/components/<ComponentName>/`. **The `.emb.*` file's basename must exactly match `meta.name`** — the build enforces this (e.g. `KpiTile.emb.ts` ↔ `name: 'KpiTile'`). `meta.name` is also the workspace identifier — see [Safety](#safety-rules). One component per directory.
## The two authoring patterns
Pick deliberately — full detail and templates in [references/component-anatomy.md](references/component-anatomy.md) and [references/extending-pro.md](references/extending-pro.md).
- **Pattern A — new component.** A React `index.tsx` + an `*.emb.ts` with an inline `defineComponent(Component, meta, config)`. Use for brand-new charts (composing `remarkable-ui` primitives), controls, and presentational components. This is the documented boilerplate pattern.
- **Pattern B — extend a Pro component.** A `definition.ts` that **spreads** an existing Pro component's exported object (`...barChartDefaultPro.meta`, `...barChartDefaultPro.config`), overriding only what changes; an `*.emb.ts` that re-exports `preview`/`meta` and calls `defineComponent`; and `index.tsx` only if you wrap with new UI. Highest reuse, lowest risk.
## Reuse-first decision tree
Work top to bottom; stop at the first match. This is the heart of the skill.
1. **Can an existing Pro component do it with configuration alone?** Check the candidates in `node_modules/@embeddable.com/remarkable-pro/dist/meta/index.json`. If yes → no code; this is a `dashboard-as-code` task, not a component task. Tell the user.
   - **Comparison / "this period vs last" is already a whole Pro family — do not rebuild it:** `KpiChartNumberComparisonPro` (delta KPI), `LineChartComparisonDefaultPro` and `LineChartComparisonWithKpiTabsPro` (overlay current + prior period), all driven by `ComparisonPeriodSelectFieldPro` via a `primaryDateRange` + `comparisonPeriod` input pair. Only build custom if the *visualization* is genuinely novel — mechanic in [references/data-loading.md](references/data-loading.md). Same for grouped/stacked category comparison: `BarChartGroupedPro`/`BarChartStackedPro` already exist.
   - **"Over time" / "time-series X" is usually not a new component.** The existing bar/line/area charts already accept a `time`/date dimension on the axis (with a granularity sub-input) — a "time-series bar chart" is just the bar chart with a date dimension. Configure the existing one; don't split out a time-series twin.
2. **Is it a *tweak* to an existing Pro component** (custom sort, a threshold annotation, an extra input, a small UI addition around it)? → **Pattern B (extend)**. See [references/extending-pro.md](references/extending-pro.md).
3. **Is it a new *visualization*, but `remarkable-ui` has the primitive** (`LineChart`, `BarChart`, `KpiChart`, `Markdown`, table primitives…)? → **Pattern A**, composing the primitive + Pro built-ins + `ChartCard`. Model on `examples/timeseries-chart/` (with `useFillGaps`) or `examples/kpi-tile/`.
4. **Is it an interactive control/filter** (dropdown, picker, button bar) that should drive other widgets? → **Pattern A**, emphasis on **events + variables**; wrap in `EditorCard`. Model on `examples/control-with-variable/`. Read [references/events-and-state.md](references/events-and-state.md).
5. **Is it presentational/content** (text, callout, layout) with little or no data? → **Pattern A**, minimal — often `props: (inputs) => ({ ...inputs })`, no `loadData`. Model on `examples/presentational-callout/`.
This tree exists to stop you **reinventing what already exists** — not to talk a genuine requirement out of being built. If nothing above fits, a custom Pattern A component **is** the right answer; build it well. **For the foundation of a genuinely novel viz, work the ladder — don't default to hand-rolled SVG:** first a **Chart.js controller already in the bundle** (many "novel" types are just a controller `remarkable-ui` doesn't wrap, and a raw Chart.js chart inherits the tooltip/hover/touch/legend/resize behaviour *and* Pro's global plugins — disable the unwanted ones); then HTML/CSS; then a permissively-licensed charting library (a new dependency is a real trade-off — surface it); last, hand-rolled SVG (you then own the **entire** interaction layer). Full ladder, licensing, and when-to-ask: [references/discovery-and-validation.md](references/discovery-and-validation.md) → "Choosing a foundation for a novel viz". **Whatever the rung, still wrap it in `ChartCard` and wire the Pro built-ins** (formatter, i18n, colours) so it belongs — the renderer supplies geometry + interaction; the content stays Pro.
## Rebuilding ≠ starting from a blank canvas
Sometimes the tree lands on Pattern A *because* an existing Pro component almost fits but can't be extended. Don't hand-roll from scratch — that's how a custom component ends up looking foreign. **Mirror the original:**
- **Reuse the same `remarkable-ui` primitives it's built from.** Pro components are mostly thin compositions of `remarkable-ui` primitives — find which ones the closest component uses ([references/discovery-and-validation.md](references/discovery-and-validation.md)) and build on those, not bespoke HTML.
- **Match its styling** — the same CSS-variable tokens, spacing, and structure ([references/theming.md](references/theming.md)).
- **Hand-roll only the genuinely new part**, as fully as the requirement needs. Mirroring sets the foundation and the look; it doesn't shrink the feature.
## Don't fight a primitive's built-in interactions
Mirroring a primitive means inheriting its **behaviour**, not just its markup. A `remarkable-ui` primitive often binds its own click/keyboard handlers on the very surfaces you'll want to fill — a table header **is** a sort `<button>`, a body cell carries a copy `<button>`, a row has its own click. Overlay your own interaction there and you either **nest interactive elements** (invalid HTML → the DOM splits → the primitive's sort/click silently breaks) or collide two click meanings on one element. This is the single most common way a custom component breaks a primitive.
**Before** attaching a handler to, or injecting interactive JSX into, **any** primitive surface (header / cell / row / trigger):
- **Audit what the primitive already binds** — read its *implementation*, not just its types (a slot typed `ReactNode` gives no hint that it renders inside a `<button>`). How: [references/discovery-and-validation.md](references/discovery-and-validation.md) → "Audit a primitive's interactions"; known traps are catalogued in [references/events-and-state.md](references/events-and-state.md) → "Interactive surfaces a primitive owns".
- **Never nest interactive elements** (`<button>` / link / `role="button"` / input inside another).
- **Render your affordance in a non-conflicting element, or use the primitive's own callback** (`onSortChange` / `onRowIndexClick` / `onCellClick`) — e.g. put rich cell content in the column `accessor` and keep `title` a plain string.

Flip side — **wire what the primitive forces on you.** Some interactions are *always-on* and can't be disabled (every table column header is a clickable sort caret — there is no `sortable: false`). The primitive only *reports* these via a callback; it does **not** act on them — so if you surface one you must wire it through to do its job (sort → Embeddable state → `loadData({ orderBy })`), or you ship a control that visibly does nothing. Worked example: [references/events-and-state.md](references/events-and-state.md) → "Wire the interactions a primitive forces on you".
## Workflow
1. **Clarify intent — the data *shape*, not specific data.**
   - Establish how many dimensions/measures and their **roles** (slice vs size, a breakdown series, a time axis) — never *which* concrete member; slots are generic (building-block principle above) and asking is bothering the user for nothing. The preview uses the library's `previewData.*` mocks; build a mock yourself only for a type the library doesn't ship (e.g. a dated time series, per `examples/timeseries-chart/`).
   - Establish **what other parts of the dashboard should react to it** — this decides events vs internal state (step 6) and picks a **single owner** for each interaction's filtering (emit it up *or* filter this component, not both).
   - An **aesthetic brief** ("a *beautiful*/slick/stunning radial chart") asks for *polish on a working, interactive chart* — not a bespoke illustration; polish amplifies a correct foundation, it doesn't replace tooltips and interaction.
   - **Default, don't interrogate.** A standard data-viz has *solved* defaults — apply them and build: generic data slots, an **always-on hover/touch tooltip**, **and** a **click event emitted up with no `variables`** — a chart does both of those last two, exactly like Pro's charts (they're orthogonal, never an either/or). Reserve questions for a **genuine fork** — real ambiguity in *what* you're building, or a dependency/licensing decision — never for defaults the skill already settles.
2. **Discover what's available.** Don't invent import names. See [references/discovery-and-validation.md](references/discovery-and-validation.md):
   - Extendable Pro components + their input schemas: read `node_modules/@embeddable.com/remarkable-pro/dist/meta/index.json`, then `<Name>.meta.json` for the one you're extending.
   - Importable utilities/types/components: the public surface is `node_modules/@embeddable.com/remarkable-pro/dist/index.d.ts` and `@embeddable.com/remarkable-ui`'s types.
   - **If a `dist/meta` or `dist/index.d.ts` read fails, stop and tell the user which package needs installing/updating — never guess at exported names.**
3. **Run the decision tree** and pick Pattern A or B.
4. **Data models are optional context — don't depend on them.** The component previews on `previewData.*` mocks and builds with **no `*.cube.yml` in the repo**. *If* cubes exist, you may skim `src/embeddable.com/models/cubes/*.cube.yml` to set realistic `defaultValue`s and sanity-check a type the viz requires (respecting `public: true` / primary-key rules and that only joined cubes query together). Never a prerequisite.
5. **Generate the files** under `src/embeddable.com/components/<Name>/`. Compose `meta` from shared `inputs`; put `loadData` in the descriptor; keep the React component focused on rendering + the Pro built-ins. Make it **fill its fixed-height box and resize** — the canvas never grows a widget to fit content, so overflow must **scroll** internally. See [references/sizing.md](references/sizing.md). Use the matching example as a scaffold.
6. **Decide internal-state vs. emit for every interaction** using the rule below and [references/events-and-state.md](references/events-and-state.md). This is where most components go wrong. Before wiring any interaction onto a primitive surface, audit what it already binds ("Don't fight a primitive" above).
7. **Run the generation checklist** in [references/checklist.md](references/checklist.md).
8. **Validate.** Run `npm run embeddable:build` (local-only, safe — never `push`/`dev`). Fix any type/registration errors. If `embeddable:dev` happens to be running, check its events log per [references/discovery-and-validation.md](references/discovery-and-validation.md).
9. **Bring up the sandbox.** See [references/sandbox.md](references/sandbox.md). In brief: if `sandbox/` isn't present, scaffold it from the skill template (`cp -r .claude/skills/build-component/sandbox-template sandbox && cd sandbox && npm install`); run `npm run dev` inside `sandbox/` (Vite on `http://localhost:5210`).
10. **Self-verify the full declared surface in the sandbox.** Not just the happy path — exercise **every** behaviour the component declares: each event's payload, each variable, every state→`loadData` transition, resize, the value reveal actually triggered, dark mode toggled. The complete item list is the sandbox section of [references/checklist.md](references/checklist.md) — run it. Fix anything that misbehaves before handing off. (This is agent diligence, not an automated gate — the user's visual pass is next.)
11. **Hand off, outcome-first.** In **plain text** (no AskUserQuestion): "*<Name> is ready!*" — stating what step 10 verified — plus numbered options: check it yourself in the sandbox at `http://localhost:5210` / inspect the code or ask about it. **No build narrative** — foundation, built-ins, and decisions are explained only when asked. Exact template in [references/sandbox.md](references/sandbox.md). The user confirms the **look, theming, and feel** (the judgment calls automation can't make) — not done until they do. The agent never runs `embeddable:push`.
## The internal-state vs. emit rule
For **every** user interaction, ask: *does this only change what THIS component shows, or does it express intent that other widgets should react to?*
- **Only affects this component** (query shape, view, a draft being assembled — e.g. a granularity toggle, a search box re-querying its own options, a table page/sort, half-built filter rows) → **Embeddable State**: the `[state, setState]` tuple in `props`; state changes re-run `props` and trigger new `loadData`. No event.
- **Other widgets should react** (a selection, a clicked data point, a committed filter) → **emit an event**: the component calls an `onX` callback, `config.events` shapes the payload (`Value.noFilter()` for cleared), and `meta.events` declares it. Whether you **also** declare `meta.variables` depends on what the component *is*: a **control** (dropdown/picker/slider/filter) exists to produce a reusable value → **declare the variable** (seeded by an input, updated by the event); a **chart/data-viz** → **emit the event and stop — no `meta.variables`**; the dashboard author wires the click, exactly like Pro's own charts. Depth: [references/events-and-state.md](references/events-and-state.md) → "Variables are for controls, not charts".
- **This decision is about clicks/selections only** — the hover/touch tooltip is an always-on legibility default ([references/sizing.md](references/sizing.md) → Legibility), *not* an alternative to emitting. A standard chart ships **both**; never frame "tooltip vs. click event" as a choice or a user question.
Components routinely do **both** internal-state and emit at once — but "both" means *different* concerns (a draft held in state, emitted only on commit), never the same selection applied twice. **One owner per selection:** once an interaction emits up, this component doesn't *also* filter its own query with it — if it should re-filter, the dashboard wires the emitted variable back into one of its inputs. Full rule + the drag-to-zoom worked example: [references/events-and-state.md](references/events-and-state.md) → "One owner per selection".

## Safety rules
- **`meta.name`** is the workspace component identifier. Renaming or deleting it after push creates a new component and orphans the old one (breaking dashboards that placed it). Treat as effectively immutable once pushed; confirm with the user before changing.
- **Don't run `embeddable:push` or `embeddable:dev`/`dev`** automatically (root `CLAUDE.md`). `embeddable:build` and `ct` are safe.
- **Custom types are beta** — TS noise, may need a `dev` restart, not supported in Custom Canvas. Use only when an input genuinely needs a fixed named option set; otherwise prefer native types. See [references/inputs.md](references/inputs.md).
## Out of scope
- Dashboards / `*.embeddable.yml` (layout, wiring widgets together, drilldowns) → the `dashboard-as-code` skill.
- Cube data models (`*.cube.yml`) → the `create-models` skill.
- Workspace styling (`embeddable.theme.ts`, `themes/`) → the `theming` skill. 
- **Fixing bugs in `@embeddable.com/remarkable-pro` / `@embeddable.com/remarkable-ui`** → fix them **centrally** in those repos so every consumer gets the fix; don't clone-and-patch here as a workaround (a local copy fragments the fix and drifts from the library). Legitimately *extending* Pro for new behaviour — Pattern B — is in scope; the line is "new capability" vs "patch a defect". When you spot a library defect, help the user report it upstream with a prefilled GitHub issue link — see [references/reporting-upstream.md](references/reporting-upstream.md).
