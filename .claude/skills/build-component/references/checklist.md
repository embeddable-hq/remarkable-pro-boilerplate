# Generation checklist
The final gate of the [SKILL.md](../SKILL.md) workflow (step 7). Before declaring a component done, confirm:
- [ ] Lives in `src/embeddable.com/components/<Name>/`; `meta.name` is unique (cross-checked against `dist/meta/index.json` and other local components) **and exactly matches the `.emb.*` filename**.
- [ ] `meta` uses `as const satisfies EmbeddedComponentMeta`; `defineComponent(...)` is called **inline** in the `.emb.ts` (never assigned to a variable first — it breaks the build).
- [ ] `meta` composes shared `inputs`/`subInputs` where they exist, rather than hand-written input objects.
- [ ] **Data inputs are generic typed slots**, not bound to specific data — `dimension`/`measure` accept any member of the right type (narrowed with `config.supportedTypes` only where the viz needs it); no concrete cube member is hardcoded, or asked of the user, outside the `previewData` mock and sensible defaults.
- [ ] Inputs are ordered **data-first** and use the Pro category strings (`Component Data` → `Component Header` → `Component Settings` → `Axes Settings` → `Pre-configured Variables`); every input you add yourself sets an explicit `category`. See [inputs.md](inputs.md).
- [ ] **Value colours** (a dimension value / measure) come from `getChartColors()` + `getDimensionMeasureColor(...)` (theme palette + `backgroundColorMap`) — **never** CSS tokens. See [pro-builtins.md](pro-builtins.md).
- [ ] **Chrome colours/spacing** use a self-contained component-token → base-token → literal fallback chain (`var(--em-mycomp-x, var(--em-sem-…, #hex))`) — the skill adds **no** theme-provider or styles-registry wiring to the repo; base-token names verified real (no `--em-sem-border`/`--inverse`/`status-warning`). Overriding is a consumer action via `theme.styles` (base = type-safe; component token = cast). See [theming.md](theming.md).
- [ ] **Resizes cleanly** in the widget: fills 100% of its **fixed-height box** (the canvas never auto-grows it to fit content), looks right narrow↔full-width and short↔tall, and scrolls (`overflow: auto`) where content can exceed the area (tables/SVG grids/long lists); controls fill width rather than stranding content. **Any wrapper around a chart primitive continues its flex chain** (`flex: 1 1 auto; display: flex; flex-direction: column; min-height: 0`) so the primitive still fills — a plain `height: 100%` block collapses it. See [sizing.md](sizing.md).
- [ ] **Legible as a data viz**: values readable for the medium via a *real* reveal — a chart keeps its tooltip (`showTooltips`); a **table shows values in-cell** (e.g. `HeatMap` needs `showValues: true`); a **hand-rolled viz** whose marks can't show their own value uses the **`Tooltip` primitive** (an SVG `<title>` is the a11y floor, not the value reveal) — **actually triggered** at narrow↔wide, with **no labels overlapping**. A **legend** is added only when colour encodes a series not labelled in place (multiple measures / a breakdown dimension) and is **never a stand-in for tooltips**. Charts/data-viz only. See [sizing.md](sizing.md) → Legibility.
- [ ] **Pro built-ins wired** (charts/controls): `i18nSetup` + `resolveI18nProps`, `getThemeFormatter` for every formatted value, `useFillGaps` if a time dimension, value colours via `getChartColors()`+`getDimensionMeasureColor`, `ChartCard`/`EditorCard` wrapper.
- [ ] **Chart `options` is fully theme-sourced — no literals.** On Chart.js: composed as `get<Type>ChartOptions()` (themed base + toggles) **deep-merged with** `get<Type>ChartProOptions()` (the Pro overlay is *partial* — never used alone, or the legend/tooltip lose their styling **and dark mode**); datalabels left at `display: 'auto'`. On another charting library: every styling slot (legend/tooltip/axis/grid/label) mapped to the `--em-chart-*` tokens, series via `getChartColors`/`getDimensionMeasureColor`, values via `getThemeFormatter`. **If you reuse a Pro `generateLabels` (pie/donut family), wrap it to inject a themed `fontColor`** — Chart.js legend text reads `legendItem.fontColor` with *no* fallback to `labels.color`, so it otherwise won't flip in dark mode; markers come from the dataset style, so translucent fills desync the swatches. See [pro-builtins.md](pro-builtins.md) → "Charts: the whole `options` object is a theming surface".
- [ ] **A raw Chart.js chart opts out of unwanted global plugins.** If the component builds directly on Chart.js (not a `remarkable-ui` primitive / Pro data builder), Pro's globally-registered plugins (datalabels, annotation) are disabled where they'd interfere (`plugins: { datalabels: { display: false } }`, since the chart draws its own labels). See [discovery-and-validation.md](discovery-and-validation.md) → "Audit what the library registers globally".
- [ ] If it's a **rebuild** of something resembling an existing Pro component, it reuses that component's `remarkable-ui` primitives and matches its styling, rather than hand-rolling from scratch. See [discovery-and-validation.md](discovery-and-validation.md).
- [ ] **No interaction fights a primitive.** Where the component fills a primitive slot (`title`/`accessor`/`triggerComponent`/cell/row) or attaches a click/keyboard handler to a primitive surface, the primitive's own bindings were audited (implementation, not just types) and there are **no nested interactive elements**; affordances use the primitive's callback (`onSortChange`/`onRowIndexClick`/`onCellClick`) or a non-conflicting element. See [events-and-state.md](events-and-state.md) → trap slots.
- [ ] **Always-on primitive interactions are wired, not dead.** Any interaction the primitive surfaces unconditionally (e.g. the table's per-column sort caret — it can't be hidden) is wired through to actually function (sort → state → `loadData({ orderBy })`), not left reporting into state with no visible effect. See [events-and-state.md](events-and-state.md) → "Wire the interactions a primitive forces on you".
- [ ] `loadData` is in the descriptor's `props`, not in React; loading/error/empty are handled (mostly by the Card).
- [ ] Every interaction is correctly classified internal-state vs. emit.
- [ ] Each declared event has a `config.events` transformer using `Value.noFilter()` for the cleared case; each declared variable links its `inputs` default and its updating `events`.
- [ ] **Emission shape fits the requirement.** Emit a **value** (`string`/`number`/`timeRange`) when the dashboard needs the single selected dimension/measure value; emit a **`filters`** clause when the component layers several selections into one compound filter (like FilterBuilder). Driven by the user's needs — not by defaulting to either. See [events-and-state.md](events-and-state.md) → "Emit what the requirement needs".
- [ ] **Pre-configured variables only on controls.** A chart/data-viz (bar, line, table, sankey, …) emits its click/selection as an event and declares **no** `meta.variables` — the dashboard author wires the click. Only an interactive control (dropdown/picker/slider/filter) that exists to produce a reusable value declares one (seeded by an input, updated by the event). See [events-and-state.md](events-and-state.md) → "Variables are for controls, not charts".
- [ ] Required inputs and all `defaultValue`s (including sub-input defaults) are sensible.
- [ ] A `definePreview(...)` using `previewData.*` mocks (`hideMenu: true`) is exported so it renders in the builder — and it **showcases any optional/per-column feature** (e.g. a link column's `linkUrl`), since the sandbox seeds its data inputs from this preview, so configured columns render there too. **For a time dimension the preview must be time-typed** — a dimension with `nativeType: 'time'` + a `granularity` and **dated** result rows (`previewData` ships no time mock; build it, per `../examples/timeseries-chart/`) — or the preview renders as non-date categories.
- [ ] `npm run embeddable:build` passes.
- [ ] Sandbox is running (`npm run dev` → `http://localhost:5210`).
- [ ] **Full declared surface self-verified** in the sandbox: every `meta.events` entry fires with the right payload, every `meta.variables` entry updates, every interactive element works, every state→`loadData` transition shows correctly sorted/filtered/paginated data, narrow↔wide resize is clean, the value reveal is **actually triggered** (hover/touch a mark → a real tooltip with the right value, per the legibility item above), **dark mode is toggled and the chrome flips** (legend text, axis ticks, and tooltip all re-colour), no secondary region (legend/side panel) is stranded behind an unreachable local scroll at narrow sizes, and the console is error-free — not just the happy path (SKILL.md workflow step 10).
- [ ] User has confirmed the component looks correct in the sandbox at `http://localhost:5210` before push is considered.
